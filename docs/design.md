# Design contracts

These contracts describe the implementation boundaries that keep request handling, ownership, and failure propagation explicit. Start with [Development](development.md) for build and verification commands, or [Writing and publishing](writing.md) for the public content model.

## Memory and runtime requirements

Keep memory use small and predictable. Allocations need a clear purpose, an explicit owner and lifetime, appropriate size bounds, and a defined release point. Avoid retaining site data beyond its useful lifetime. Caching and preloading require a concrete benefit that justifies their memory cost and invalidation complexity; they are not default implementation choices.

Bounded temporary buffers are acceptable when they serve a concrete purpose, such as separating Markdown rendering from page assembly. Consider peak live memory, including concurrent requests, before adding full-document copies. Release temporary decoding, title, and rendering storage promptly. Avoid imposing a particular buffer arrangement when a simpler implementation has reasonable, bounded memory costs. Rendering failures must still discard incomplete output rather than send partial HTML as a successful response.

Document, template, and asset edits must appear on the next uncached request. They must not require a restart or rebuild. Keep presentation in editable site files rather than compiled C strings. Configuration and root selection may remain startup state, but that does not justify retaining the contents of those files.

Review memory ownership, peak live allocations, and release paths when changing a subsystem. Explain material increases in memory use and the benefit they provide. Prefer straightforward code with justified memory use over either unnecessary retention or elaborate machinery whose sole purpose is eliminating a temporary allocation.

## Subsystem boundaries

`configuration` owns parsed strings, directory order, and navigation entries. Parsing accepts a byte span and base directory, performs no filesystem access, and returns either a fully usable configuration or an empty object. Loading implements file discovery and bounded reading around that parser. The executable supplies fixed defaults; the same search routine accepts isolated paths in tests.

`document` owns descriptor-relative lookup and reading. Resolution receives an already decoded path, immutable configuration, and a borrowed content-root descriptor. Every result is initialized, owns any returned descriptor and location buffer, and must be released even after failure. Outcomes distinguish a document, redirect, invalid request, missing document, and internal failure.

`url` owns path validation, canonical document URLs, and link rewriting. Rewriting is independent of destination existence. It identifies the decoded `.md` suffix before validating the rest of the path, so extensionless links and asset/external URLs remain unchanged even with malformed percent escapes. For local Markdown destinations, it resolves against the source filename, normalizes segments within the root, strips the source extension, maps indexes to directory URLs, percent-encodes the resulting path, and preserves queries/fragments. A dot in the final public path component denotes an extension and is rejected. The resolver and HTTP adapter enforce that rule independently of link rendering.

`renderer` owns per-parse state and HTML emission. MD4C supplies borrowed, length-delimited strings, which are never assumed to be NUL-terminated or retained after callbacks. Parser-identified entities are decoded using a generated HTML5 lookup before escaping attributes or rewriting links. Rich image labels emit escaped text into `alt` attributes; ordinary raw HTML events remain verbatim elsewhere because publishers are trusted.

The same parse collects plain text from the first Markdown heading for the page title. Span formatting and raw HTML tags are omitted, entities are decoded, and soft breaks become spaces. Missing or empty headings fall back to the extensionless document basename. After parsing, the renderer passes the body and title to `page_template` and enforces the configured limit on the complete expanded page. Temporary body, title, and page buffers remain request-owned and bounded. The rendered body and assembled page coexist during expansion so MD4C parses once, even when a template repeats the content. Their peak memory cost must be considered alongside concurrent requests; temporary body, title, and template storage is released before sending the response.

`page_template` reads the required `[site] template` file for each render. Its C++17 adapter uses unmodified Inja and nlohmann/json headers from the root-level `inja/` submodule. After parsing, it releases the read buffer before allocating metadata or expanding the page. Parsed source, syntax trees, and JSON metadata remain local to the expansion and are then released. Title/site values, navigation, and error metadata are copied into JSON; the rendered Markdown body stays borrowed and `{{content()}}` writes it directly into the final bounded response buffer. Inja autoescapes ordinary string substitutions, including both quote characters. No complete intermediate rendered page or JSON body copy is created. Stream failures stop evaluation, and all C++ exceptions are caught at the C interface and mark output failed. Startup parses the template and checks representative document/error paths with and without navigation, then releases the temporary state. Arbitrary expressions may select other paths at request time. There is no compiled-in page layout, retained template cache, fallback template path, or automatic filesystem include loading.

The template author remains trusted. The output budget bounds response bytes, not all of Inja's internal allocations: syntax trees, JSON copies, and expression results use the C++ heap, and functions such as `range()` can allocate arrays before emitting output. This tradeoff is accepted for authored templates. Inja also does not check all arithmetic errors; authors must avoid signed integer overflow and remainder by zero. Keep upstream dependencies unmodified rather than carrying local fixes.

`server` adapts these subsystems to CivetWeb. A `begin_request` callback completes document responses or returns zero for unencoded static paths. Encoded asset paths are mapped to validated filenames and passed to CivetWeb's `mg_send_mime_file` API. CivetWeb owns connections, worker threads, and static MIME/range/HEAD response handling, with listings and script recognition disabled. An `http_error` callback sends established-request errors through the shared shell and response helper, correcting CivetWeb 1.16's default HEAD error body. That callback uses the opposite return convention: zero means the error was handled.

## Ownership and sequencing

The main thread loads configuration, applies scalar CLI overrides, checks and releases the page template, and either checks the roots or enters `server_run`. Configuration remains immutable while serving and is freed after the server returns. Startup validates disjoint roots, opens the Markdown root, builds static mappings, blocks termination signals before worker creation, initializes CivetWeb file support, and starts the listener. Template edits appear on the next uncached request without restarting or rebuilding the binary.

Workers inherit blocked SIGINT/SIGTERM. The main thread uses `sigwait`, so cleanup never runs in an asynchronous signal handler. On termination, `mg_stop` joins workers before application-owned descriptors or configuration are released. Partial startup failures unwind only acquired resources. SIGPIPE is ignored so a disconnected reader cannot terminate the process during a write.

Each request owns its route descriptor, source bytes, rendering state, and output. It reads from the descriptor opened during resolution, avoiding a second path lookup. Read failures, callback cancellation, allocation failures, and limit failures discard partial output and produce an independent error response. Renderer callbacks report failure with negative return values and mark the output buffer failed, including when a temporary buffer or link rewriter fails. The final render checks both the parser status and the sticky flag because MD4C 0.4.8 can discard positive callback errors. HEAD renders identically to GET to preserve status and content length but sends no body. Error pages have a separate bounded budget so an output-limit failure can still produce an error.

Buffers own allocations, check arithmetic before growing, and retain a sticky failure flag. Callers borrow data only until mutation or release. Appends do not support overlapping input and destination allocations.

## Filesystem and HTTP policy

Markdown paths reject NUL/control bytes, hidden components, backslashes, repeated separators, and dot segments. Each component is opened with `O_NOFOLLOW`; intermediate components must be directories and the final descriptor must identify a regular file. `O_NONBLOCK` prevents FIFOs from blocking before validation. Missing, inaccessible, or forbidden content is absent; resource and other I/O failures remain internal errors.

Automatic URI decoding is disabled because CivetWeb 1.16 decodes `request_uri` and `local_uri_raw` in place before invoking application callbacks. An embedded NUL would otherwise hide the remainder from `strlen` and routing. Stories preserves the original encoded `local_uri_raw`, calls `mg_url_decode` once with form decoding disabled, and validates the returned byte span before any decoded C-string operation. This rejects encoded NULs while allowing literal percent escapes such as `%2500` and preserving literal plus signs. Queries remain opaque and undecoded. Resolver fuzzing begins at the validated, decoded-path boundary; HTTP regressions cover the decoder boundary itself.

Only `/assets/` permits static fallback and extension-bearing resource names. Its sole filesystem root comes from configuration; there are no compiled-in asset paths, runtime fallback directories, or separate built-in asset namespace. Pico CSS is an ordinary file at `pico.min.css` in that root. Before delegating an asset, the HTTP adapter rejects HTML and XHTML according to CivetWeb's MIME classification. Static index lookup is disabled so an extensionless directory URL cannot implicitly serve an HTML file. The asset root contains public files and must not overlap content. Asset symlinks follow CivetWeb's behavior. Script recognition is disabled even when the installed library includes scripting support. Stories completes all other routes, including 404s.

Configuration is startup state; content is read on every request. Publish complete files by atomic replacement to avoid partially rewritten documents. Replacing files inside the content root is supported; replacing the root itself requires restart because the server retains its descriptor. Proxy and client caches may continue serving cached responses.

## Verification boundaries

C tests exercise production subsystem contracts. Python tests drive the built binary using temporary roots and ephemeral ports. Readiness and shutdown deadlines prevent indefinite waits. Raw socket checks verify HEAD bodies independently of client-library behavior.

Fuzz harnesses use the production resolver, link rewriter, and parser, checking semantic invariants alongside sanitizers. Resolver setup opens an immutable fixture root once. Inputs do not write files, start servers, or open network connections. A separately instrumented core keeps libFuzzer's main and coverage runtime out of the server binary. Checked-in seeds remain immutable; working corpora and artifacts live in the build tree.
